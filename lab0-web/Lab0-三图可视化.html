# Lab0 材料一：Shell 执行 `echo hi` 的全系统控制流图

**观察范围**：从用户在终端输入 `echo hi` 并按回车，到屏幕出现 `hi` 与换行、子进程退出、父进程完成 `wait`。本图依据本地 `xv6-riscv` 参考树；它不是当前 Lab1 裸机内核的运行轨迹。

**图例**：`U/用户栈`=用户态及当前进程用户栈；`S/进程内核栈`=S 态及当前进程内核栈；`S/调度器栈`=S 态及当前 CPU 调度器专用栈。锁栏写该节点的关键持锁；`无`表示该节点不持有自旋锁，不能理解成整个函数从不加锁。启动时 M 态只用于配置和 `mret`，下列命令链发生在 U/S 态。

```mermaid
flowchart TD
  A[终端输入 echo hi 和回车] --> B[sh getcmd/gets: read fd0 每次 1 字节\nU/用户栈; 无锁]
  B --> C[usys.S: a7=SYS_read; ecall\nU→S; 硬件保存 sepc/scause/sstatus]
  C --> D[trampoline uservec 保存通用寄存器到 trapframe\n切到 sh 内核栈和内核页表]
  D --> E[usertrap→syscall→sys_read→fileread→consoleread\nS/sh 内核栈]
  E --> F{cons.r == cons.w?}
  F -- 是 --> G[sleep_prepare &cons.r; 释放 cons.lock; sleep→sched→swtch\nsh:SLEEPING; S/sh 内核栈→调度器栈]
  G --> H[scheduler 选择其他 RUNNABLE 进程\nS/调度器栈]
  A --> I[UART 收到字符，经 PLIC 外部中断]
  I --> J[devintr→uartintr→consoleintr\nS/当前被中断进程的内核栈; cons.lock]
  J --> K[回车使 cons.w=cons.e; wakeup &cons.r\nsh→RUNNABLE]
  K --> L[scheduler→swtch 恢复 sh; consoleread 返回\nS/sh 内核栈→userret/sret→U]
  H -->|中断唤醒后再选中 sh| L
  L --> M[sh 解析 echo hi; fork1→fork ecall\nU→S/sh 内核栈]
  M --> N[sys_fork→kfork→uvmcopy; 复制 trapframe; filedup\n父返回子 pid; 子的 a0=0]
  N --> O[父 sh: wait ecall→kwait→sleep_prepare/sh→sleep\nS/sh 内核栈→调度器栈]
  N --> P[子 echo 前身: scheduler→forkret→userret/sret\nS/调度器栈→子内核栈→U/子用户栈]
  P --> Q[runcmd→exec echo; ecall→sys_exec→kexec\nS/子内核栈; 替换用户映像]
  Q --> R[userret/sret→echo 的 start/main\nU/echo 用户栈]
  R --> S[write 1,hi,2; write 1,换行,1\n各自经 ecall→usertrap→sys_write]
  S --> T[filewrite FD_DEVICE→devsw CONSOLE.write\n→consolewrite→uartwrite→UART THR]
  T --> U[屏幕显示 hi 和换行]
  U --> V[echo exit ecall→kexit; fileclose; ZOMBIE; wakeup sh\nS/echo 内核栈→调度器栈]
  V --> W[sh kwait 被唤醒; freeproc 回收子进程\n返回 sh 用户态并再次显示提示符]
```

## 时序与边界标注

| 时序 | 当前执行体与关键调用 | 特权级／栈 | 持锁与状态变化 |
|---|---|---|---|
| 1 | `sh: getcmd→gets→read(0,&c,1)`；每次系统调用读取一个字符 | `U/sh 用户栈` → `S/sh 内核栈` | 用户态无自旋锁；陷入硬件只记 `sepc/scause/sstatus`，`uservec` 才逐个保存通用寄存器。 |
| 2 | `usertrap→syscall→sys_read→fileread→devsw[CONSOLE].read→consoleread` | `S/sh 内核栈` | `consoleread` 持 `cons.lock` 检查输入环形缓冲。空缓冲时登记 `&cons.r`，释放 `cons.lock`，再 `sleep→sched→swtch`；`sched` 切换时只持 `sh->lock`，并将 `sh` 置为 `SLEEPING`。 |
| 3 | 终端设备收到各字符；UART/PLIC 外部中断使当前 CPU 进 `kerneltrap` 或 `usertrap`，再经 `devintr→uartintr→consoleintr` | 被打断处若为 U 则 `uservec` 换至**被打断进程**内核栈；若为 S 则 `kernelvec` 留在其当前内核栈／调度器栈 | `consoleintr` 持 `cons.lock`；它会回显字符。回车时 `cons.w=cons.e` 并 `wakeup(&cons.r)`，短暂获得各 `p->lock`，把 sh 标为 `RUNNABLE`。 |
| 4 | 调度器再次选中 sh；`consoleread` 将字节拷给用户缓冲，读到换行返回。`usertrap→prepare_return→userret→sret` | `S/调度器栈` → `S/sh 内核栈` → `U/sh 用户栈` | `scheduler` 选进程时持该 `p->lock`，恢复后由进程侧释放；返回 U 前无自旋锁。 |
| 5 | sh 对非内建命令执行 `fork1`；`sys_fork→kfork` | `U/sh 用户栈` → `S/sh 内核栈` | `kfork` 复制页表和 `trapframe`，`filedup` 增文件引用计数；复制父 `ofile` 指针；设置子 `a0=0`，父得到子 PID。子标记 `RUNNABLE`。 |
| 6 | 父 sh 调用 `wait→sys_wait→kwait`；子由 `scheduler→forkret` 首次运行，回到用户态后 `runcmd` | 父：`S/sh 内核栈→调度器栈`；子：`调度器栈→S/子内核栈→U/子用户栈` | 父等待时持 `wait_lock` 扫描子进程；登记睡眠通道 `sh` 后先放 `wait_lock` 再睡。子第一次运行经 `forkret` 释放由 `scheduler` 带过来的 `p->lock`。 |
| 7 | 子 `exec("echo", argv)`：`sys_exec→kexec` 读取 ELF，建立新页表和栈，然后替换旧地址空间 | `U/子用户栈` → `S/子内核栈` → `U/echo 用户栈` | `exec` 保留 PID、父子关系、`ofile`、`cwd`，替换 `pagetable`、`sz`、入口 PC 和用户 SP；文件系统路径上短时持 inode 睡眠锁／日志事务。 |
| 8 | 当前树 `echo.c` 对 `hi` 调用一次 `write(1,"hi",2)`，随后另一次 `write(1,"\n",1)` | 各次 `U/echo 用户栈` → `S/echo 内核栈` | `sys_write→filewrite(FD_DEVICE)→consolewrite→uartwrite`。`uartwrite` 使用 **`tx_lock` 睡眠锁**串行输出，不持自旋锁睡眠；硬件暂忙则在 `&tx_chan` 睡眠，由 UART 发送中断唤醒。 |
| 9 | UART 驱动写 `THR`，终端显示 `hi\n`；echo `exit→kexit`，sh 的 `kwait` 回收它 | echo：`S/echo 内核栈→调度器栈`；sh：`S/sh 内核栈→U/sh 用户栈` | `kexit` 逐一 `fileclose`，唤醒 sh，设置 `ZOMBIE`；`kwait` 持 `wait_lock` 和子 `p->lock` 完成 `freeproc`，父重新显示提示符。 |

## 三处推演批注

1. **read 的阻塞边界**：`sleep_prepare` 与 `sleep` 分两步，期间 UART 中断可能先 `wakeup`。`wakeup` 清 `p->chan`，随后 `sleep()` 发现它为 0 就不真正睡下，避免丢失唤醒；sh 不会永远卡在 `read`。
2. **输出并非单次 `write(1,"hi\n",3)`**：此版本 `echo.c` 对参数与换行分开调用 `write`。图中把它们画成两次陷入，否则与源码不符。
3. **wait 与 exit 的竞态**：如果子在父进入 `wait` 前已退出，它保持 `ZOMBIE`；`kwait` 扫描时直接回收。若父先睡下，`kexit` 的 `wakeup(p->parent)` 再唤醒父，两条路径都成立。

# Lab0 材料二：exec 完成后、echo 首条用户指令前的数据结构全景快照

**截面定义**：选单核的一条合法时序：sh `fork` 后先进入 `wait` 并睡眠，调度器随后运行子进程；子进程在 `kexec("echo", argv)` **刚提交新映像**（`p->pagetable = pagetable; p->sz = sz;`）且尚未执行 echo 首条用户指令的瞬间。此刻 CPU 仍在子进程的 `S` 态内核栈，稍后 `sys_exec` 返回、`prepare_return→userret→sret` 才进入 echo。PID 与物理页号取决于运行时分配，因此图中使用符号，不伪造固定数值。

## A. 进程表与引用全景

```mermaid
flowchart LR
  CPU[CPU0: S态; echo 子进程内核栈] --> E[proc E: echo前身; RUNNING]
  I[proc I: init; SLEEPING 于 wait] --> S[proc S: sh; SLEEPING 于 wait]
  S -->|parent| I
  E -->|parent| S
  I -->|pagetable| IPT[init 页表]
  S -->|pagetable| SPT[sh 页表]
  E -->|pagetable| EPT[新 echo 页表]
  E -->|trapframe| ETF[echo trapframe: epc=elf.entry; sp=argv栈; a1=argv]
  E -->|ofile 0,1,2| F0[共享的 console file 对象]
  S -->|ofile 0,1,2| F0
  I -->|ofile 0,1,2| F0
  F0 -->|ip| IN[console 设备 inode; T_DEVICE; major=CONSOLE=1]
  F0 -->|major| DEV[devsw 1: consoleread / consolewrite]
```

| `proc` | `state` / `parent` | `pagetable` / `sz` | `ofile[0..15]` |
|---|---|---|---|
| init (`I`) | `SLEEPING`，`parent=0`；本时序正等待 sh | `PT_init`；`sz_init` 为 init 映像大小，非 echo 大小 | 0、1、2 指向 console 的 `file` 对象 `F`；3–15 为 `0`，假定此时没有其他打开文件。 |
| sh (`S`) | `SLEEPING`，`parent=I`；`chan=S`（`kwait` 等 echo） | `PT_sh`；`sz_sh` 为 sh 的用户空间大小 | 0、1、2 指向 `F`；3–15 为 `0`（命令 `echo hi` 不重定向、不建管道）。 |
| echo 子进程 (`E`) | **`RUNNING`**，`parent=S`；尚在 `kexec` 的 S 态路径上 | `PT_echo_new`；`sz_echo=G+2×PGSIZE`，其中 `G=PGROUNDUP(最后一个 PT_LOAD 段结束 VA)`，`USERSTACK=1` | `kfork` 的 `filedup` 使 0、1、2 继续指向 `F`；`exec` 不清空文件描述符；3–15 为 `0`。 |

`proc` 是全局 `proc[NPROC]` 表；每条记录还含 `pid`、`kstack`、`trapframe`、`context`、`cwd`。`E` 的内核栈与 `trapframe` 是 `allocproc` 分配的；`kexec` 用新页表替换旧页表，但不换这个内核栈。`E->trapframe->epc=elf.entry`，`sp` 指向新用户栈中的参数区，`a1` 指向 `argv`；随后 `syscall()` 把返回的 `argc` 写入 `a0`。同一时刻只有该 CPU 上的 `E` 处于 `RUNNING`；多核情况下其他状态可能不同，本图固定单核时序。

## B. echo 用户页表的 Sv39 映射树

`MAXVA = 0x4000000000`，`PGSIZE = 0x1000`，所以 `TRAMPOLINE = 0x3ffffff000`，`TRAPFRAME = 0x3fffffe000`。以 `[起点,终点)` 表示区间。

```text
PT_echo_new  (Sv39 根页表，satp.PPN 指向物理根页)
├─ L2[PX(2,va)] → L1[PX(1,va)] → L0[PX(0,va)] → 低地址用户叶 PTE
│  ├─ ELF PT_LOAD 段页：各段 [ph.vaddr, PGROUNDUP(ph.vaddr+ph.memsz))
│  │  ├─ 代码页：V|R|X|U（若段仅可执行）；实际权限按 ELF ph.flags 转换
│  │  └─ 数据/BSS 页：V|R|W|U（若段可写）
│  ├─ [G, G+0x1000)       栈 guard 页：V|R|W，PTE_U=0
│  └─ [G+0x1000,G+0x2000) 用户栈：V|R|W|U，sp 位于此页
├─ 未映射空洞：(G+0x2000) ... 0x3fffffe000
│  └─ 堆：本截面尚未单独分配；后续 sbrk 从当前 sz 扩展，可能出现 V|R|W|U 的页
├─ L2/L1/L0 → [0x3fffffe000,0x3ffffff000) TRAPFRAME：V|R|W，PTE_U=0
└─ L2/L1/L0 → [0x3ffffff000,0x4000000000) TRAMPOLINE：V|R|X，PTE_U=0
```

| 区域 | 虚拟地址与物理对象 | 权限／解释 |
|---|---|---|
| 代码、只读数据及可写数据 | 由 `echo` ELF 的各个 `PT_LOAD` 的 `ph.vaddr/ph.memsz/ph.flags` 决定；不能凭源码猜固定边界 | `uvmalloc` 基础权限 `V|R|U`；段若有 `EXEC` 再加 `X`，若有 `WRITE` 再加 `W`。不同段的实际权限应按 ELF 标志逐一标。 |
| guard 页 | `[G,G+0x1000)`；物理页存在 | `uvmclear` **只清 PTE_U**，故不是完全未映射；用户访问触发异常，S 态仍可访问。 |
| 用户栈 | `[G+0x1000,G+0x2000)`；`USERSTACK=1` | `V|R|W|U`；`sp` 在该页，字符串与 `argv` 从高地址向低地址排布。 |
| 堆区 | `sz=G+0x2000` 以上的可扩展空间；本截面无独立堆页 | 不是把 guard 与用户栈之间误标成堆；后续 `sbrk` 才增长 `sz`，此版可能按需懒分配。 |
| trapframe | `[0x3fffffe000,0x3ffffff000)` → `E->trapframe` 物理页 | `V|R|W`，无 `U`；trampoline 代用户在 S 态保存/恢复寄存器。 |
| trampoline | `[0x3ffffff000,0x4000000000)` → 全进程共用 trampoline 代码物理页 | `V|R|X`，无 `U`；S 态陷入/返回路径用；**不随 fork 复制物理代码页**。 |

每一个有效叶 PTE 还包含物理页号 PPN；中间级 PTE 只有 `V` 并指向下一级页表页。`proc_pagetable` 在新页表上先映射 trampoline 和 trapframe；`kexec` 再映射 ELF 和栈；旧页表在提交后释放。图中 `sz` 是进程已使用用户地址空间的高水位，**不是整张页表的顶端**，因为 trapframe/trampoline 固定在接近 `MAXVA` 的高地址。

## C. 文件描述符、file 表与 inode 快照

```text
init.ofile[0] ─┐
init.ofile[1] ─┤
init.ofile[2] ─┤
sh.ofile[0..2] ├──> ftable.file F {type=FD_DEVICE, ref≈9,
echo.ofile[0..2]┘                     readable=1, writable=1,
                                      major=CONSOLE(1), ip=I_console}
                                           │                   │
                                           │ip                 └──> devsw[1]
                                           v                        read=consoleread
                              inode I_console {type=T_DEVICE,     write=consolewrite
                              major=1, minor=0, ref=...}
                                           │
                                           └──> consolewrite→uartwrite→UART0 THR
```

`init` 启动时 `open("console",O_RDWR)` 得到 fd 0，`dup(0)` 两次得到 1、2；sh 从 init 的 `fork` 继承同一 `F`，echo 从 sh 的 `fork` 再继承它。若只有这三个进程且均未另开文件，`F.ref=9`（三个进程各三个描述符）；它是一个**条件性快照值**，而不是 inode 的 `ref`。`F.ip` 指向磁盘文件系统中代表设备节点 `console` 的 inode；`FD_DEVICE` 写操作按 `major=1` 分派到 `devsw[1].write=consolewrite`，不是按普通文件偏移写入数据块。`cwd` 各自还引用根目录 inode，与 fd1 的设备 inode 不同。

## 推演批注与答辩点

1. **为什么 `exec` 后还能输出到 fd1？** `kexec` 只提交新用户映像和寄存器入口；`proc.ofile` 保留。`kfork` 早已对共享 `file` 调用 `filedup`。
2. **guard 页究竟“无效”还是“不可给用户访问”？** 此树 `uvmclear` 仅清 `PTE_U`，页仍有 `V|R|W`；“未映射 guard”是对本实现的不精确表述。
3. **子进程退出会泄漏 stdout 吗？** `kexit` 遍历 `ofile` 执行 `fileclose`，`F.ref` 按描述符递减；最后一个引用离开时才 `iput(F.ip)`。父进程 `wait` 回收的是 `proc` 与页表，文件引用在 `exit` 已处理。
4. **为何 trampoline 不复制物理页？** 所有进程的页表映射到同一只读可执行内核代码页；需要隔离的是每个进程自己的 trapframe 数据页。

# Lab0 材料三：一次用户态时钟中断到 `sret` 的微观旅程

**选定现场**：单核 CPU0 正在 U 态运行普通用户进程 `P`，当前使用 `P` 的用户页表与用户栈；`stvec` 已由上次 `prepare_return` 指到 trampoline 的 `uservec`。时钟中断 `scause=0x8000000000000005`；可能存在其他 `RUNNABLE` 进程 `Q`。此参考树用 S 态 `stimecmp` 触发时钟中断，进入陷阱后执行主体在 **S 态**，不是全程 M 态。

```mermaid
sequenceDiagram
  participant U as P 用户指令/U/用户栈
  participant HW as RISC-V 硬件
  participant TV as trampoline.S:uservec
  participant KT as trap.c:usertrap/devintr
  participant SC as proc.c:sched/scheduler
  participant RT as prepare_return/userret
  U->>HW: 时钟中断到来
  HW->>TV: scause=0x800...005; sepc=受中断PC; SPP=U; SIE→SPIE; 进入S态并跳stvec
  TV->>TV: sscratch暂存a0; 保存用户通用寄存器到P.trapframe
  TV->>KT: sp=P.kstack顶部; 切内核satp; jalr usertrap
  KT->>KT: stvec=kernelvec; 保存sepc到trapframe.epc
  KT->>KT: devintr识别时钟; clockintr更新ticks/唤醒并重设stimecmp; 返回2
  KT->>SC: which_dev=2; yield: P→RUNNABLE; sched→swtch
  SC->>SC: 调度器在专用栈运行; 可选Q; 后来再选P
  SC->>KT: swtch恢复P内核context; yield返回
  KT->>RT: prepare_return: 关中断; stvec=uservec; 设置trapframe.kernel_*、SPP=U、SPIE=1、sepc
  RT->>TV: usertrap返回用户satp; userret切用户页表并恢复通用寄存器
  TV->>U: sret: PC=sepc; 恢复U态中断状态; 从原指令位置继续
```

## 逐步状态记录

| 步骤 | 动作与寄存器／内存变化 | 特权级、页表、栈、锁 |
|---|---|---|
| 0 | `P` 正在用户指令流；`satp=P.pagetable`，`stvec=uservec`，`sscratch` 可由入口使用。 | `U`、`P` 用户页表、`P` 用户栈、无自旋锁。 |
| 1 **硬件陷入** | 硬件将当前 PC 写入 `sepc`，把中断原因写入 `scause=0x8000000000000005`，`sstatus.SPP` 记录原模式 U，`SPIE←SIE`，清 `SIE`，切到 S 态并跳 `stvec`。**硬件不会自动切栈、切页表，也不会保存全部通用寄存器。** | 刚到 `uservec` 时是 `S` 态，但仍在 `P` 用户页表、原用户 `sp`；无锁。 |
| 2 **汇编保存** | `uservec` 先用 `sscratch` 暂存用户 `a0`，将 `a0=TRAPFRAME`；把 `ra/sp/gp/tp/t0...t6` 等用户通用寄存器写到 `P.trapframe`，最后将原 `a0` 存入偏移 112。 | `S`，仍使用 `P` 用户页表；trapframe 是 `P` 私有页的高地址映射，`PTE_U=0`，S 态可写；尚未用内核栈。 |
| 3 **转到 C** | 从 trapframe 取 `kernel_sp/kernel_hartid/kernel_trap/kernel_satp`；`sp=P.kstack+PGSIZE`，`tp=hartid`；`sfence.vma`，写 `satp=kernel_satp`，再 `sfence.vma`，`jalr usertrap`。 | `S`、内核页表、`P` 内核栈；无自旋锁。trampoline 在两套页表同一 VA 映射，切页表前后均可执行。 |
| 4 **分类中断** | `usertrap` 验证来自 U 态，将 `stvec` 改为 `kernelvec`，保存 `sepc` 到 `P.trapframe->epc`；`devintr` 匹配时钟中断，调用 `clockintr`。CPU0 更新 `ticks`，唤醒等待 tick 的进程，重设 `stimecmp=r_time()+1000000`，返回 `which_dev=2`。 | `S/P` 内核栈；`clockintr` 更新 `ticks` 时短暂持 `tickslock`，`wakeup(&ticks)` 可能短暂持被检查进程的 `p->lock`；返回后均已释放。 |
| 5 **主动让步** | `usertrap` 看到 `which_dev==2` 调 `yield`；`yield` 持 `P->lock` 将 `P->state=RUNNABLE`；`sched` 验证只持这把锁且中断关闭；`swtch(&P->context,&cpu->context)` 仅保存/恢复内核 callee-saved 寄存器、`ra/sp`。 | `S/P` 内核栈 → `S/CPU 调度器栈`；切换交接期间持 `P->lock`，调度器返回该 `swtch` 后释放。**用户完整现场在 trapframe，不在 context。** |
| 6 **调度决定** | `scheduler` 扫描 `proc[NPROC]`，逐个持 `p->lock` 找 `RUNNABLE`，标 `RUNNING` 并 `swtch`。可先运行 `Q`，也可稍后再次选择 `P`；不保证这次 tick 一定换到别的进程。 | `S/调度器栈`；选中进程时持它的 `p->lock`，新进程侧负责放锁。 |
| 7 **恢复 P 的内核续点** | 某次扫描再次选中 `P`，`swtch` 读回 `P->context`，从先前 `sched` 的调用点继续；`sched→yield` 返回，`yield` 释放 `P->lock`，回到 `usertrap`。 | `S/P` 内核栈、内核页表；释放后无自旋锁。 |
| 8 **准备返 U** | `prepare_return` 关中断，将 `stvec` 指回 trampoline `uservec`；将下次陷入需要的 `kernel_satp/kernel_sp/kernel_trap/kernel_hartid` 写入 `P.trapframe`；设置 `sstatus.SPP=0`、`SPIE=1`，`sepc=P.trapframe->epc`。`usertrap` 返回 `MAKE_SATP(P.pagetable)` 给 `userret`。 | `S/P` 内核栈、内核页表；无自旋锁。时钟中断不是 `ecall`，**`epc` 不加 4**。 |
| 9 **汇编返 U** | `userret` 执行 `fence.i`、切到 `P` 用户页表并刷新 TLB，按 trapframe 恢复用户通用寄存器和 `sp`，最后恢复 `a0`；执行 `sret`。硬件按 `sepc` 恢复 PC，按 `SPP=0` 进入 U 态，并由 `SPIE` 恢复中断使能。 | `S` 的 trampoline → `U/P` 用户页表与用户栈；无自旋锁；继续执行被中断位置。 |

## 现场区分与推演批注

1. **硬件与软件各保存什么？** 硬件自动处理 `sepc/scause/sstatus` 等陷阱控制状态，`trampoline.S` 负责全部通用寄存器；`swtch.S` 只负责内核上下文，因此不能拿 `context` 代替 `trapframe`。
2. **为什么不能像系统调用那样 `epc += 4`？** 时钟中断异步发生，硬件记录的是应当继续执行的用户 PC；回到硬件提供的 `sepc` 才能保持连续性。此树只在 `r_scause()==8` 的 `ecall` 分支把 PC 加 4。
3. **为什么返回前要重新写 `stvec`？** 内核期间若再次陷入应进 `kernelvec`；返 U 前改回 `uservec`，下一次用户陷入才能通过 trapframe 安全换栈和页表。
4. **为什么 `yield` 不等于“必定换人”？** `scheduler` 只按扫描顺序选 `RUNNABLE`；若没有其他候选或扫描再次到 `P`，CPU 可以继续运行同一个进程，但仍经历一次让步与上下文切换链路。
